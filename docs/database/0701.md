# 一、锁

## （一）为什么要有锁？

### 1、防超卖、防丢失更新

两个人同时改成同一个值，其中一个会被覆盖

### 2、保证读到的是最新数据

不加锁时，读到的可能是旧快照。

## （二）锁的类型

按粒度分

表锁：锁整张表。全表 update 时，或索引失效时

行锁：锁一行。走索引的 update。。。where id=？

间隙锁：锁索引区间之间

按模式分

共享锁（S）：别的事务能读，不能写

排他锁（X）：别的事务不能读，不能写

按思想分

悲观锁：先加锁再操作。适合冲突多，事务短。

乐观锁：不加锁，提交时用版本号比对。适合冲突少，可重试。

## （三）唯一索引：最轻量的分布式锁

### 1.为什么唯一索引能防重复？

多台机器同时插入同一行，InnoDB 在插入时回检查唯一键。第一个事务拿到锁并插入成功，第二个事务回阻塞在该索引记录上，直到第一个事务提交后抛出 DuplicateKeyException。

## （四）条件更新（CAS）：比 version 更轻的乐观锁

update ... set status=1 where id=? and status=0

影响行数=1-》抢到了

影响行数=0-〉别人已经抢到了

## 乐观锁 vs 悲观锁

|        | 乐观锁                            | 悲观锁             |
| ------ | --------------------------------- | ------------------ |
| 锁对象 | 数据版本                          | 数据库行锁         |
| 冲突时 | 更新影响行数 0 行，自己重试或退出 | 阻塞等待           |
| 适用   | 冲突少、任务短                    | 冲突多、必须成功   |
| 风险   | 冲突高了空转                      | 长事务锁超时，死锁 |

调度器的场景：冲突其实是“我本不该执行”，而不是“我要等别人”。

所以选乐观锁，抢不到就退出，这才是对的语义。
